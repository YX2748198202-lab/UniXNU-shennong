# fi139 结果与下一步

## 结论

常驻段改造把三个 ledger 模板搬进了 `__PORT_CONST`，而 `ledger.c` 的段归属检查只认 `__DATA_CONST`，两者契约不一致——这是 fi138 停机的直接原因，不是随机种子、也不是 PAC。

本轮把契约改成「两段都接受」，并按源码里全部三处调用点（`finalize`、`copy` 的目标与源）分别派生原生检查，保留原来三条断言与全部失败路径。派生件已用新 256 字节种子打包，并对 `9f72e95c` 执行了唯一一次临时启动，命令返回 0。

**能说的**：镜像内容、派生正确性、断言保留、种子契约、FAT 一致性都已实测通过（14 项验收全过）。
**不能说的**：fi139 没有越过 ledger。命令返回 0 只证明 fastboot 交接完成，不证明内核前进了。

## 与历史最好成绩的关系

2026-11-05 的旧基线确实通过过阶段 C，到过 `bsd_init` 之后的根设备挂载（`Failed to mount root device @IOKitBSDInit.cpp:984`）。那是 iPadOS 时代的配置。当前 iPhone iOS 27 / arm64e 这条线上，fi139 仍是**比历史最好成绩更早**的位置——修好 ledger 只说明清掉了一个已知路障，不等于追平。

## 下一步

1. 取 fi139 的完整画面。若停在 `ledger_template_finalize` 或 `ledger_template_copy` 的同一断言，说明段边界本身算错，要回到 `__PORT_CONST` 的实际映射范围核；若停在新位置，按新 `PC` 继续。
2. 若 ledger 已过，下一批同类风险是其它仍只认 `__DATA_CONST` 的段归属断言——用同一套三处检查的做法先全量扫一遍源码里的 `require_data_const` 类断言，避免一次只修一个。
3. 顺手补 `crypto-hmac.json` 与内核的对应关系，避免以后误判加载器是否校验它。
4. 恢复向阶段 C 推进：`machine_startup` → `kernel_bootstrap` → `bsd_init` → 根卷挂载。根卷到这一步才用到。
