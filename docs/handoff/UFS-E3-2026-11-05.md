# UFS root bring-up on SM8650 (shennong / Xiaomi 14 Pro) — 2026-11-05

This note documents one day of work on the E3 stage of UniXNU-shennong: getting XNU to
mount a root device from a UFS partition on a Snapdragon 8 Gen 3 device. It is written as
a reference for other ports of the same phone (23116PN5BC) and for other SM8650 boards,
because most of the time was spent on gates that are not device specific: how the UFS
driver gets its IOStorageFamily symbols, how the prelink relocates kexts, and how the
driver's owner-signed root policy works.

**State at the end of the day:** the storage stack is proven end to end on the device
(controller, clocks, PHY, SMMU, GPT, manifest, both root windows configured and attached);
the only remaining gate is publishing the root windows, which needs the signed policy
bundle described below. `Mu-policy12.img` carries that bundle and was booted; its screen
had not been photographed yet when this was written.

## The stack, and what each layer needed

| Layer | What it does | What it needed here |
|---|---|---|
| `ShengUfs` driver (feed `99d8bcd3`) | SM8550/SM8650 UFS host: GCC clocks, PHY, command queues, SMMU bypass context, SHNGROOT root volume reader | Its 190 IOStorageFamily vtable slots and 6 VerifiedRoot symbols are absolute addresses, not imports; they have to be measured per build |
| `prelink` | Places every component of the kernel image at `kernelcache address + slide` | Bindings must be measured for the *built* image, not for the original kernelcache |
| SHNGROOT manifest | Fixed 4 KiB block at the start of the `userdata` partition: `"SHNGROOT"`, version, count, image size, then 128-byte entries per window/object | Windows keep their offsets when objects are appended, so per-block hashes stay valid |
| `VerifiedRoot` kit | 160-byte signed header + 384-byte RSA-3072 signature + per-4096-byte-block SHA-256 table; published as the driver's root policy | This board had no bundle at all, so nothing could be published |

## What the device printed, round by round

Each row is one `fastboot boot`; the quoted text is the screen, not a log.

1. `native-ufs-probe=10` —
   `smmu: conflicting UFS stream mapping slot=2 smr=80000060 s2cr=2 @NativeUfs.cpp:405`.
   The controller and PHY come up. The bootloader leaves an exclusive SMR for the UFS
   stream (`0x60`) pointing at context bank 2 **with translation enabled**, and the
   planner only accepts a free bank or one already in bypass.
   Fix: `patches/ufs-smmu-takeover.patch` takes the exclusive bank over — disable its
   translation, program it as the VA64 bypass context, reuse the existing mapping. This is
   the same approach the reference marble port uses.

2. `native-ufs-probe=10`, after the patch — `block0 magic 474e4853 544f4f52`,
   `manifest status=0 windows=2`. GPT parses, the written SHNGROOT volume reads back,
   both windows (`OS`, `SystemOS`) are present. From here on the *storage* side never
   regressed; every later failure was above it.

3. `native-ufs-root=1` — `Undefined kernel instruction: pc=0xfffffff00596ed98 instr=0
   @sleh.c:1045`. That address is the bound `IOBlockStorageDevice` constructor, and the
   bytes there were zeros.

   Why: `scripts/scan-prelink-storage.py` measures the dispatch table in the original
   kernelcache, but the prelink places every component at `original + slide`
   (`board.toml [kernel.prelink] slide = "-0x1000000"` for this board). The built image
   proves it: the IOStorageFamily text hashes to the pin's `852b7846…` at
   `0xfffffff00496c000`, exactly 16 MiB below the kernelcache address.

   A trap worth recording: the *symbol table of the built image still carries the
   unrelocated addresses*, so looking up `__ZTV20IOBlockStorageDevice` there agrees with
   the kernelcache and will convince you the pin is right. Locate the kext bytes instead.

   Fix: `scripts/apply-prelink-slide.py` applies `[kernel.prelink] slide` to the measured
   pin, **and the result must be committed** — the build links the committed pin and only
   measures afterwards, so an uncommitted measurement is a wasted round.

4. `native-ufs-probe=12 native-ufs-diagnostics=1` —
   `UFS ROOT FAILURE: root window preparation failed`, `stage=policy count invalid`,
   `policies=0`, with `HC cap=f5c7031f ver=00000400`, `CMD op=28 ocs=00`,
   `SMMU smr=80000060 s2cr=2 cbar=10000 sctlr=0`, `GPT lba=227e00
   userdata=227e00..3d14ffa`, `magic=474e4853 544f4f52`, `manifest=0`, `WINDOWS found=2`
   all green. `configureVerification` requires 1..16 owner-signed policies.

5. Attempts to bypass the policy (compile flag `NATIVE_VERIFIED_BLOCK=0`, then source
   patches) reached `stage=signed window identities`, `prepared=2 published=0` — both
   windows configured and attached, but `validate()` in an unverified build returns false
   by design ("Root publication requires owner verification in every build"). Those
   bypasses were removed; they also taught that a flag-only change does not invalidate
   `libShengUfs.a` (it stayed at 514,920 bytes across a "rebuilt" round).

6. The real bundle (described below), three rounds to get the root image right:
   * `stage=owner signature and hash table`, `verify=00000004` (VR_HASH_TABLE),
     `prepared=1`: the OS window verified, SystemOS did not. Reading the image back showed
     `SystemOS.vroot` written 753,376 bytes away from the offset the manifest named — the
     appender opened the image in append mode, so `seek` was ignored and every write went to
     end-of-file.
   * `stage=root manifest rejected`, `manifest=4`: the driver's bounds check needs
     `image_bytes` to be a multiple of 4096 and every entry offset 4 KiB aligned.
   * Final round — **`published=2`, `reads=142 failures=0 media=7`**:

     ```
     disk1  EF57347C-… size=c4e00000  uuid=E886F82C-…
     disk3  EF57347C-… size=16a400000 uuid=50F8067F-…
     disk1s1 41504653-… size=c4e00000  uuid=8846FE78-2910-42…   (SystemOS policy UUID)
     disk3s1 41504653-… size=16a400000 uuid=04769D26-2CA0-4…    (OS policy UUID)
     disk2  GUID_partition_scheme / disk2s1 7C3457EF-… (APFS)
     ```

     Both root windows are published as IOMedia with the UUIDs the policy signed, APFS
     reads their partition tables, and the `probe=12` report thread then panics to show it.

## Building the root policy bundle

Two pieces of information can only come from the device's own data:

* **APFS volume UUID per window.** The OS window is a GPT disk with one APFS partition
  (type `7C3457EF-0000-11AA-AA11-00306543ECAC`, first LBA 34 here), SystemOS is a bare
  container. The volume superblock is found by scanning for its `APSB` magic and checking
  the object type (`0xd`, filesystem) and `fs_index`; the UUID sits at `+0xF0`. APFS then
  reports the same UUID on the `IOMedia`, which is what the driver matches.
* **The per-block hash table.** Every 4096-byte block of each window is hashed. On this
  board: OS 6,077,580,800 B → 1,483,785 blocks (47,481,120 B table), SystemOS
  3,303,014,400 B → 806,400 blocks (25,804,800 B table). 11.7 s locally.

`scripts/make-root-policy.py` produces:

```
key (395 B)      "VROOTKEY" + modulus[384] big-endian + exponent 0x010001
header (160 B)   "VROOT01\0" | u32 version=1 | u32 160 | u32 4096 | u32 flags=0
                 | u64 image_bytes | u64 block_count | volume_uuid[16]
                 | image_sha256[32] | hash_table_sha256[32] | key_sha256[32]
                 | u64 generation
signature (384B) RSA-3072 PKCS#1 v1.5 over SHA-256(header)
```

`vr_open` checks, all of which were verified locally against a public key rebuilt from
the blob before anything was committed (16/16): key magic, modulus top bit and oddness,
exponent, `SHA-256(key) == header[120:152]`, header shape, `block_count ==
ceil(image_bytes / 4096)`, `generation >= 1`, volume UUID, hash-table digest and the
signature itself.

The 395-byte public key and the two 544-byte headers are committed under `policies/`.
The private key is **not** in this repository (gitignored `*.rsa`, kept in the local build
workspace): regenerating the bundle needs it, booting the board does not.

Keeping the tables out of the kernel (the "header-only" form) means the kernel embeds 544
bytes per window and reads the table back from the root image object `<window>.vroot`
(`NativeUfs::readPolicyTable`). `scripts/unixnu/userdata.py` only writes objects when the
image is created, and rebuilding it means re-reading the whole IPSW, so
`scripts/add-root-policy-objects.py` appends them in place: windows keep their offsets (so
their hashes stay valid), the manifest is rewritten as version 2 with the object entries,
and the manifest's own trailing SHA-256 is recomputed.

## Reproducing a round

```bash
# fetch the kernel artifact and repack it with the arguments
scripts/fetch-artifact.sh <run-id> /tmp/ufs.zip
unzip -o -q /tmp/ufs.zip '*/payload/payload.img' -d /tmp/work
python3 scripts/patch-payload-args.py --payload /tmp/work/…/payload.img --set-args "<args>"
python3 scripts/repack-v0-bootimg.py \
  --template /mnt/c/Users/yoox/AppData/Local/Temp/unixnu-shennong/Mu-shennong-smp.img \
  --payload /tmp/work/…/payload.img --out /tmp/Mu.img

# regenerate the policy bundle after the root image changes
python3 scripts/make-root-policy.py --image <root.img> --report <userdata-root.json> \
  --key <private key> --out <dir>
python3 scripts/add-root-policy-objects.py --image <root.img> \
  --object OS.vroot=<dir>/OS.vroot --object SystemOS.vroot=<dir>/SystemOS.vroot

# hand the device to WSL and boot
/mnt/c/Program\ Files/usbipd-win/usbipd.exe detach --busid <busid>
/mnt/c/Windows/System32/wsl.exe -u root -- /usr/lib/linux-tools-6.8.0-147/usbip attach -r <host> -b <busid>
/mnt/c/Windows/System32/wsl.exe -u root -- <platform-tools>/fastboot boot /tmp/Mu.img
```

The usbip busid changes between reboots (`4-1` → `5-1` observed); `usbipd list` shows the
live one. Windows `fastboot.exe` could not see the device on this host (no WinUSB
binding), so the WSL path is the one used.

## Build-pipeline traps, for the next person

1. Any input the build consumes but the pipeline measures must be **committed before the
   build that uses it**, or the round links stale data.
2. A compile-flag change does not touch source timestamps: delete the archive directory or
   the old `.a` is linked again. The same applies to generated sources — the workflow now
   rewrites `build/verified-root/policies` and drops the generated policy file so the
   archive is rebuilt against the bundle.
3. `build-xnu-4k-baseline.sh` only links the archives behind its own switches; the
   workflow force-loads `libVerifiedRoot.a` and `libStorageBindings.a` explicitly.
4. The macOS runner shell is `bash -e`, so a scan that fails must still print its log.
5. Never trust a symbol table for a relocated image; find the bytes.
