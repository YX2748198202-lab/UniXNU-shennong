## What the root policy is, and why it exists

The UFS driver publishes a root window only against an owner-signed envelope
(`kits/VerifiedRoot`): a 160-byte header (image size, block count, volume UUID, image and
hash-table digests, key digest, generation) followed by a 384-byte RSA-3072 signature, with
the per-4096-byte-block SHA-256 table either appended or read back from a `<window>.vroot`
object inside the root image. This board had no bundle at all, which is why every publish
attempt stopped at the policy check.

`scripts/make-root-policy.py` builds the bundle from the written root image:

* the APFS volume UUID is parsed out of the window image (the OS window is a GPT disk with
  one APFS partition; SystemOS is a bare container) — the driver compares it against the
  UUID APFS reports for the media;
* every 4096-byte block of each window is hashed (OS 6,077,580,800 B → 1,483,785 blocks,
  SystemOS 3,303,014,400 B → 806,400 blocks; 11.7 s locally);
* the header is filled and signed with RSA-3072.

The 395-byte public key blob and the two 544-byte headers are committed under `policies/`.
The private key is **not** in the repository (gitignored `*.rsa`, kept at
`.artifacts/policy/root-key.rsa`); regenerating the bundle needs it, booting does not.

All of `vr_open`'s checks were verified locally before anything was committed, against a
public key rebuilt from the blob: key magic, modulus top bit and oddness, exponent 0x010001,
`SHA-256(key) == header[120:152]`, header shape, `block_count == ceil(image_bytes/4096)`,
generation, volume UUID, hash-table digest and the RSA signature — 16/16.

## Reproducing a round

```bash
# 1. fetch the kernel artifact and repack it with arguments
scripts/fetch-artifact.sh <run-id> /tmp/ufs.zip
unzip -o -q /tmp/ufs.zip '*/payload/payload.img' -d /tmp/work
python3 scripts/patch-payload-args.py --payload /tmp/work/…/payload.img --set-args "<args>"
python3 scripts/repack-v0-bootimg.py \
  --template /mnt/c/Users/yoox/AppData/Local/Temp/unixnu-shennong/Mu-shennong-smp.img \
  --payload /tmp/work/…/payload.img --out /tmp/Mu.img

# 2. hand the device to WSL and boot it
/mnt/c/Program\ Files/usbipd-win/usbipd.exe detach --busid <busid>
/mnt/c/Windows/System32/wsl.exe -u root -- /usr/lib/linux-tools-6.8.0-147/usbip attach -r <host> -b <busid>
/mnt/c/Windows/System32/wsl.exe -u root -- .artifacts/platform-tools/fastboot boot /tmp/Mu.img
```

The busid changes between reboots (`4-1` → `5-1` observed); `usbipd list` shows the live one.

## Pipeline traps met today (each cost a build; do not reintroduce)

1. An input the build consumes but the pipeline measures must be **committed before the
   build that uses it** — the slide-corrected pin was produced by CI but not committed, so
   one round linked the old addresses.
2. Changing a compile flag does not touch source timestamps: delete the archive directory
   or the old `.a` is linked again. A file-flag change also does not invalidate
   `build-verified-root/verified-root-policies.cpp`; the workflow now rewrites the bundle
   input and removes the generated source.
3. The binding scan measures the original kernelcache; the prelink slides every component by
   `[kernel.prelink] slide`. Verify a measurement by locating the kext bytes in the built
   image (the IOStorageFamily text hashes to the pin's value at `0xfffffff00496c000`) —
   symbol tables keep the old, unrelocated addresses and will mislead you.
4. `build-xnu-4k-baseline.sh` only links the archives behind its own switches, so
   `libVerifiedRoot.a` and `libStorageBindings.a` are force-loaded by a workflow step.
5. The runner shell is `bash -e`: a scan that fails must still print its log key (`tail`).
6. Windows `fastboot.exe` cannot see the device on this host (no WinUSB binding); WSL over
   usbip works but one transfer dropped mid-flash. Re-flashing is safe; verify 34/34 chunks.
